# Option C capture Inbox contract

This is the first web/native capture slice. Web actions and the future authenticated `/api/mobile/v1` capture routes call the same server-only functions in `src/lib/captures/service.ts`. Mobile authentication and routes are owned separately; this change does not add token auth or mobile endpoints.

## Service interface

```ts
createCapture(input: {
  url: string;
  text?: string;
  note?: string;
  source?: "WEB" | "IOS_SHARE";
  clientRequestId: string;
  canonicalEmployerUrl?: string;
}) -> Capture

listCaptures(options?: { limit?: number; cursor?: string })
  -> { items: Capture[]; nextCursor: string | null }

getCapture(id: string) -> Capture | null

updateCapture(id: string, input: {
  text?: string;
  canonicalEmployerUrl?: string; // empty clears it
}) -> Capture

markCaptureFailed(id: string, reason: string) -> Capture
```

The Prisma `Capture` fields are `id`, `clientRequestId`, `originalUrl`, `dedupeUrl`, `canonicalEmployerUrl`, `text`, `note`, `source`, `ingestionState`, `ingestionError`, `createdAt` and `updatedAt`. The current Dossier deployment has one authenticated account, so `clientRequestId` is unique for that instance. If Dossier adds multiple accounts, scope both idempotency and dedupe keys to the account before enabling that model.

`clientRequestId` is generated by the client and must be reused on retries. A repeated request ID returns its existing row without changing its data. `dedupeUrl` is independently unique and canonicalizes host case, `www`, trailing slashes, fragments and common tracking parameters. `originalUrl` always keeps the initially shared link. A later duplicate can fill fields that were empty, but does not replace the original URL or overwrite nonempty user text.

## Validation and state

Inputs accept only `http` or `https` URLs without embedded credentials. URL fields are limited to 2,048 characters, posting text to 100,000, notes to 2,000, and request IDs to 128. No capture operation performs network access.

The ingestion state is distinct from `ApplicationStatus` and any employer-submission outcome:

| State | Meaning |
| --- | --- |
| `SAVED` | The capture is persisted and waiting for user review. |
| `NEEDS_DETAILS` | A LinkedIn share has neither pasted posting text nor a user-supplied official employer URL. |
| `READY` | User-supplied posting text or an official employer URL is available for the existing preparation flow. |
| `FAILED` | A future explicit ingestion attempt failed; `ingestionError` contains a bounded, user-safe reason. |

There is no automatic LinkedIn discovery or logged-in LinkedIn access. A LinkedIn URL-only capture stays saved as `NEEDS_DETAILS`; the user can paste the official posting text or add its official employer URL. The capture Inbox does not fetch URLs. If the user chooses the existing fetch action in New application, it uses the existing safe posting fetch, which validates addresses for each request and redirect.

## Web handoff

`/captures` lists captures and `/captures/[id]` edits the text or official employer URL. The detail page continues with `/new?capture=<capture-id>`. The `/new` page now explicitly resolves that capture server-side and passes its content through the existing `fromPosting` draft mechanism. It passes only the user-supplied canonical employer URL as the preparation URL; a LinkedIn URL is never forwarded to the posting fetch action.

The capture itself is not an application. The current New application flow only creates an application after its existing review and document-writing steps complete.
